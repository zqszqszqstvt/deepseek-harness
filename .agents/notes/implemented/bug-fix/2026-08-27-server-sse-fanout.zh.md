# Agent Note: Server SSE 扇出

Status: implemented

[English](2026-08-27-server-sse-fanout.md) | 中文

## Problem

多用户 Server 的每个 `/events` 响应都会各自打开一条覆盖所有会话的 `ApiProxy.events.mux()` 流。因此，ApiProxy 会为每个已连接用户分配一个 `FrameQueue` 并安装完整的全局事件监听器，而 Server 只会在其他会话的帧进入各队列后才将其丢弃。每个活跃用户各有一个 SSE 响应时，每个全局事件都会在过滤前复制到所有连接，因此聚合 CPU 和瞬时内存会按全局事件速率乘以连接数增长，并可能随活跃用户增加而接近平方级增长。每个响应队列也没有上限，缓慢或停滞的客户端可以无限保留编码后的事件。

## Decision

Server 拥有一条延迟启动、进程级共享的 ApiProxy mux 读取器，并只把各个会话范围内的帧分发给为该会话注册的 SSE 客户端。ApiProxy mux 约定及其 Web、CLI、SDK 和插件消费方保持不变。Server 生成的 `session/subscribed` 帧使用目标会话的当前序号，共享读取器则忽略 ApiProxy 面向所有会话的订阅帧。

分发器为每个会话只保留最新的 `session/queue` 和 `session/jobs` 快照，以及仍在等待处理的审批和提问请求。重连会在合成的订阅帧之后收到这份瞬时基线；持久事件和投影继续通过既有 history 与投影路径恢复。已解决的交互帧会删除匹配的缓存请求，会话 dispose（资源释放）会删除该会话的全部缓存状态和订阅方。

每个 SSE 响应都有按字节计量的待发送帧上限。超过上限会关闭该响应，而不是静默丢弃事件，使客户端可以重连并重新建立 history 和瞬时状态。Server 也会拒绝超过进程级和单用户上限的连接。CLI（命令行界面）选项 `--max-sse-connections`、`--max-sse-connections-per-user` 和 `--sse-buffer-bytes` 的默认值依次为 `128`、`2` 和 `1048576`；`/readyz` 会报告当前连接数、全局上限和共享 mux 状态。Server dispose 会中止共享读取器并等待其退出后再完成。

## Verification

Server HTTP 测试会同时打开 Alice 和 Bob 的响应，证明 ApiProxy 只收到一次 mux 调用，并证明每个响应只收到自己会话的帧。测试还覆盖未解决交互的重放及解决后的移除、进程级和单用户连接拒绝、就绪状态计数、队列溢出，以及 Context dispose 达到共享读取器和响应均已关闭的完全停稳状态。

## Alternatives considered

**要求每个平台后端自行打开一条共享连接并执行过滤。** 否决将其作为唯一保障，因为 Server 天然的单用户端点对于独立消费方仍不安全，而且任何一次错误集成都会恢复这种放大效应。

**为每次 ApiProxy mux 调用增加会话过滤器。** 否决，因为每个连接仍会安装并调用一套全局监听器；在帧进入队列前过滤可以减少保留帧，却无法消除事件速率乘以连接数的开销。

**修改 ApiProxy，公开新的会话专用流。** 否决，因为缺陷只存在于 Server 适配器中，修改共享宿主协议会扩大 Web、CLI、SDK 和插件的兼容与测试范围。

**在保持响应打开时丢弃慢客户端的帧。** 否决，因为仍然存活的 SSE 响应会表现为健康状态，却暴露内部不一致的事件序列，而且不会发出需要执行 history 恢复的信号。

## Consequences

无论 SSE 连接数是多少，全局 ApiProxy 事件都只会由 Server 投影并编码一次，随后仅交付给感兴趣的会话客户端。每个客户端保留的内存有明确上限，部署方也可以限制连接总量。共享读取器从第一个订阅方出现后会保持活动直到 Server 关闭，使瞬时状态能为后续重连保持最新；其会话缓存由当前 queue/job 快照和未完成交互决定，而不保留事件历史。无法跟上流速的客户端会失去连接并必须重连；当一个会话的完整瞬时基线超过配置的缓冲区时，该会话会收到 `503`，直到部署方提高上限或瞬时状态缩小。
